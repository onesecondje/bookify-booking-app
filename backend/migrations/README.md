# SQL migrations

A migration is a versioned change to the database structure. Run pending files
from the repository root with:

```sh
pnpm -C backend db:migrate
```

The command uses `DATABASE_URL` from `backend/.env` or the process environment.
It does not start the HTTP server. Start PostgreSQL before running it.

## Files and history

Use filenames such as `0001_create_businesses_and_services.sql`, with a unique,
four-digit version followed by a snake_case description. Files run in filename
order. Add new migrations after existing ones; never rename, delete, or edit a
file that has already been applied. To change a table, create the next migration.

`schema_migrations` stores the filename, checksum, and application time of each
completed migration. A checksum is a SHA-256 fingerprint of the SQL file. The
runner rejects changed files or a history that no longer matches the file order.
Windows and Unix line endings are normalized before checksumming.

`src/migrations.ts` reads the SQL files and applies pending migrations using one
checked-out PostgreSQL connection. `src/migrate.ts` is the CLI entry point: it
reports the result and closes the pool.

## Transactions and concurrent runs

All pending SQL changes and their history entries run in a single transaction:

```text
BEGIN → Acquire migration lock → Check history → Apply pending SQL → COMMIT
                                                    Error → ROLLBACK
```

`COMMIT` makes the changes permanent. `ROLLBACK` cancels every change in this
batch, including partial table creation and history entries. A failed, uncommitted
migration can be corrected and retried. Previously committed migrations stay applied.

All statements use the same client because transactions belong to connections,
not pools. `client.release()` runs in `finally` so the client returns to the pool.
An advisory transaction lock serializes cooperating migration runners in the same
database. The key `76429761` is a shared application convention, not a password.
The lock is released on commit or rollback. Each statement has a 30-second timeout,
including lock acquisition; this is not a timeout for the entire migration batch.

This runner supports transactional SQL migrations only. Do not put `BEGIN`,
`COMMIT`, or operations that cannot run inside a transaction, such as
`CREATE INDEX CONCURRENTLY`, in these files. Automatic down migrations are not
implemented; schema changes are made by appending new forward migrations.
Migrations are run explicitly, not automatically during API startup.

## Initial schema

One business can have many services. Each service belongs to exactly one business.

| Table        | Column             | Purpose                                                   |
| ------------ | ------------------ | --------------------------------------------------------- |
| `businesses` | `id`               | UUID primary key, generated by PostgreSQL                 |
| `businesses` | `name`             | Required name that cannot consist only of ordinary spaces |
| `businesses` | `time_zone`        | Required time zone name, such as `Europe/Warsaw`          |
| Both         | `created_at`       | Creation instant, recorded with `timestamptz`             |
| `services`   | `id`               | UUID primary key, generated by PostgreSQL                 |
| `services`   | `business_id`      | Foreign key referencing an existing business              |
| `services`   | `name`             | Required name that cannot consist only of ordinary spaces |
| `services`   | `duration_minutes` | Required positive integer duration                        |
| `services`   | `is_active`        | Required boolean; defaults to `true`                      |

- A primary key identifies a row uniquely and cannot be null.
- A foreign key prevents a service from referencing a nonexistent business.
- `ON DELETE RESTRICT` prevents deleting a business that still has services.
- `NOT NULL` prevents missing values; `CHECK` enforces conditions on stored values.
  Defaults provide values when an insert omits the column.
- `timestamptz` stores an instant; display uses the database session's time zone.
  It does not retain the original IANA zone name. `businesses.time_zone` stores
  that separately. This column currently rejects blank text but does not verify
  that the value is a recognized time zone; future write validation must do so.
- The `services_business_id_idx` index helps look up services for a business.
  PostgreSQL automatically indexes primary keys, but not referencing foreign keys.
- No service prices, specialists, bookings, or sample data are included yet.

## Integration tests

```sh
pnpm -C backend test
```

Tests require the configured PostgreSQL database and a role allowed to create
schemas. Each test creates a unique `bookify_test_*` schema, directs its connections
to that schema, and removes it afterwards. Application tables and data are untouched.
If a test process is forcibly killed, a temporary test schema may remain.

Tests cover re-running migrations, constraints, rollback after a SQL error,
checksum mismatch, and concurrent migration runners.
