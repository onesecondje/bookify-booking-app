# Prisma migrations

Prisma Migrate is the only active migration runner. The old runner and its tests
have been retired; the original work remains in Git commit 8a88652.

## New databases

Run `pnpm -C backend db:migrate`. Prisma applies the baseline and subsequent
migrations, recording them in `public._prisma_migrations`. Repeated deployment skips applied migrations.
No demonstration data is inserted. Run `db:generate` separately for the client.

## Existing databases from the SQL runner

The local development database was baselined on 2026-11-10. Do not repeat adoption
there. For another database with the original SQL history:

1. Stop old migration processes and application writes. Back up the database and
   verify restoration in a separate database. Confirm the original migration's
   checksum and compare the live columns, defaults, constraints, and indexes with
   the baseline. Do not baseline a database with unexplained differences.
2. Preserve the old history outside Prisma's managed public schema:

```sql
BEGIN;
SELECT pg_advisory_xact_lock(76429761);
CREATE SCHEMA bookify_legacy;
ALTER TABLE public.schema_migrations SET SCHEMA bookify_legacy;
COMMIT;
```

3. From backend, run `pnpm exec prisma migrate resolve --applied 0_init`.
   This records the baseline without executing its CREATE TABLE statements.
4. Run `pnpm db:migrate` and `pnpm db:status`. Verify unchanged application data,
   table identities, constraints, defaults, and indexes. Inspect schema differences
   with `pnpm exec prisma migrate diff --from-config-datasource --to-schema prisma/schema.prisma --exit-code`.
   Diff does not cover unsupported features such as CHECK constraints: inspect
   PostgreSQL catalogs and test their behavior separately.

The archive and resolve operations are separate transactions. If resolve fails,
keep the archive, fix the reported problem, and resume at step 3 after checking
migration status. Do not rerun the old runner or reset the database. The archive
is a historical record, not a second active migration history. New databases do
not need that archive. Prisma manages public; do not add bookify_legacy to its datasource.

## Future schema changes

Edit schema.prisma, then from backend create a draft with
`pnpm exec prisma migrate dev --name describe_change --create-only`. Development
migration generation uses a shadow database (a disposable database for replaying
history); use a development database and the necessary database-creation permission
or a dedicated shadow database. Never point a shadow database URL at application data.
Review SQL, including preservation of CHECK constraints, before applying it with
`pnpm exec prisma migrate dev`. Stop and investigate unexpected reset prompts.
Use `db:migrate` to deploy reviewed, committed migrations to other environments.
Do not edit an applied migration. Use a new migration to change existing schema.

Prisma Migrate does not preserve our old runner's single transaction across all
pending migrations. PostgreSQL migrations can explicitly use BEGIN/COMMIT where
appropriate; operations such as CREATE INDEX CONCURRENTLY cannot run inside them.
The initial baseline contains ordinary CREATE TABLE/INDEX statements. A failed
deployment needs inspection and the documented Prisma recovery workflow, not an
automatic assumption that the entire batch was rolled back.

SQL files use LF line endings so Windows checkouts preserve Prisma checksums.
Do not use db push or migrate reset as part of routine deployment.

## Initial schema

One business can have many services. Each service belongs to exactly one business.

| Table        | Column             | Purpose                                                   |
| ------------ | ------------------ | --------------------------------------------------------- |
| `businesses` | `id`               | UUID primary key, generated by PostgreSQL                 |
| `businesses` | `name`             | Required name that cannot consist only of ordinary spaces |
| `businesses` | `time_zone`        | Required time zone name, such as `Europe/Warsaw`          |
| Both         | `created_at`       | Creation instant, recorded with `timestamptz`             |
| `services`   | `id`               | UUID primary key, generated by PostgreSQL                 |
| `services`   | `business_id`      | Foreign key referencing an existing business              |
| `services`   | `name`             | Required name that cannot consist only of ordinary spaces |
| `services`   | `duration_minutes` | Required positive integer duration                        |
| `services`   | `is_active`        | Required boolean; defaults to `true`                      |

- A primary key identifies a row uniquely and cannot be null.
- A foreign key prevents a service from referencing a nonexistent business.
- `ON DELETE RESTRICT` prevents deleting a business that still has services.
- `NOT NULL` prevents missing values; `CHECK` enforces conditions on stored values.
  Defaults provide values when an insert omits the column.
- `timestamptz` stores an instant; display uses the database session's time zone.
  It does not retain the original IANA zone name. `businesses.time_zone` stores
  that separately. This column currently rejects blank text but does not verify
  that the value is a recognized time zone; future write validation must do so.
- The `services_business_id_idx` index helps look up services for a business.
  PostgreSQL automatically indexes primary keys, but not referencing foreign keys.
- No service prices, specialists, bookings, or sample data are included yet.

## Specialists and service assignments

Migration 20261110000100_add_specialists_and_service_assignments adds specialists
and specialist_services without rewriting existing businesses or services. It is
wrapped in BEGIN/COMMIT. The baseline remains unchanged.

A specialist record belongs to one business and has a database-generated UUID,
required nonblank name, active flag (default true), and timestamptz(6) creation
instant. This represents a business's specialist entry, not a login/user account.
There is no specialist limit per business.

SpecialistService is an explicit many-to-many model: each row assigns one service
to one specialist. It stores business_id, specialist_id, service_id, and created_at.
Its composite primary key (business_id, specialist_id, service_id) rejects duplicate
assignments. A specialist may provide multiple services; a service may have multiple
specialists. No assignment implies working hours or appointment availability.

Two composite foreign keys enforce business boundaries:

- (business_id, specialist_id) references specialists(business_id, id).
- (business_id, service_id) references services(business_id, id).

Both referenced tables have an explicit unique index on (business_id, id) because
PostgreSQL needs a matching unique key for each composite reference. Although id is
already globally unique, those indexes allow the database to verify business_id
as part of the relation. UUIDs alone would not prevent cross-business assignments.
The existing services_business_id_idx is preserved.

The assignment primary key supports business/specialist lookups. A reverse index
on (business_id, service_id) supports finding specialists for a service. The
specialist composite unique index also supports business-prefixed lookups.

All new foreign keys use ON DELETE RESTRICT and ON UPDATE NO ACTION. Explicitly
remove assignments before deleting referenced specialists/services; no implicit
cascade is performed. A business with specialists cannot be deleted. Changing a
referenced business/key is blocked while assignments exist. Deactivation preserves
assignments, and assignments to inactive records are not prohibited by this schema;
future public queries/booking validation must enforce active status.

The specialist name CHECK uses length(btrim(name)) > 0, matching the existing name
constraints (ordinary spaces). It is maintained in SQL, not Prisma schema. Prisma
migration diff does not verify CHECK constraints, so integration tests exercise them.

Migration tests deploy to isolated schemas and verify Prisma relation queries,
many-to-many assignments, defaults, duplicate rejection, cross-business and missing
references, null/blank values, delete/update restrictions, indexes, and preservation
of existing data during baseline-plus-upgrade deployment.

The explicit demo seed now adds Alice and Alex and three service assignments; see
the backend README. A public specialist lookup for a selected active service is
implemented; it filters inactive specialists without deleting assignments. The public
services endpoint retains its contract. Specialist selection UI is not implemented yet.

## Integration tests

Run `pnpm -C backend test` with PostgreSQL available and CREATE SCHEMA permission.
Tests create unique bookify*test*\* schemas, set Prisma's schema URL parameter and
pg's search_path to the same schema, and remove only those schemas afterward.
They invoke the real Prisma CLI to verify repeatable deployment, baseline adoption
with existing records, defaults, all four CHECK constraints, NOT NULL, foreign keys,
delete/update behavior, and the business lookup index. Interrupted tests can leave
a temporary schema. Tests do not reset the application database.
